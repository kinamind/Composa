# 复盘与重排内部日程

复盘不是按时间自动改状态，而是基于最新事实重新判断什么已经发生、什么实现了目标、什么仍需要下一步。

## 获取上下文

用 `calendar_snapshot` 覆盖需要回顾的过去范围和接下来的相关范围；用 `memory_search`、`item_get` 和 `profile_get` 获取事项内容、已有工作段、截止、优先级与个人偏好。区分已经保存的安排和仅准备提出的建议。

## 两个独立判断

- **发生确定性**：这个事件或工作段是否很可能已经发生或结束？
- **结果确定性**：用户的目标是否已经达成，还是仍有产物、答复或后续行动？

固定会议到了结束时间，通常只能提高“事件已经结束”的置信度，不自动证明会议目标完成。高确定性且完成含义清楚时可以更新并告知，允许用户纠正；不确定时保持原状态并询问，或用 `lifecycle_followup_manage` 在更合适的时间再次复盘。后续工作应与已结束事件分开保存和规划。

## 生命周期唤醒

有明确结束边界的固定事件，以及已经保存的工作计划，在最后一个相关时段结束时由系统可靠唤醒 Agent。它保证“回来判断”，不预先决定“已经完成”，也不取代提前提醒。

收到系统生命周期事件时，时间边界本身已经成立，不必再问用户时钟是否走到了那里。结合原事项措辞、连续对话、日程变化和相关上下文判断该状态意味着什么：如果原事项只是承载一次固定发生，且没有取消、改期等相反证据，可以结束原 event 并用一句话报告；如果完成还依赖出席、产物、答复或其他未确认事实，就保持相应状态，并创建真实后续、选择稍后复盘，或只问一个会影响下一步规划的问题。工作段结束同样不等于工作目标完成，应根据实际进展证据处理。

不能把上述判断改写成事项类别、标题关键词或固定置信度表。用户可见回复只呈现状态变化、真正相关的下一步或必要问题，不展开事项详情和内部复盘过程。

非固定任务或项目的进度同步是另一条独立通道。到达 Agent 先前选择的检查点时，先用现有证据判断是否可以直接更新进展和计划；只有未知进展会改变下一步时才问一个问题。事项仍需持续承载时，再结合剩余工作、截止、依赖、日程和用户节奏决定下一个检查点；不要机械沿用上一次间隔。进度同步不能覆盖固定事件或工作段已经存在的结束复盘，反之亦然。

## 日常与周期计划

把固定事件作为承诺、deadline 作为风险边界、work session 作为已投入计划、reminder 作为通知。检查预计工作量是否在截止前得到足够工作段，发现当天变化或失败的工作段时，重新查询空档并提出或执行用户已授权的调整。

内部复盘必须检查足够范围，不能因为预设展示条数而漏判；但完整判断应留在后台状态，不等于把所有未完成、已完成和远期事项一起展示。不要按“会议”“作业”等关键词写死状态转换。事实交接只突出本轮真正相关的取舍、冲突、风险、状态变化和需要用户决定之处，其余由前台注意力层按用户意图渐进展开。
